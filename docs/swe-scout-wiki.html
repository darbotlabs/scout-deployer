Scout Architecture Intelligence

How six repositories under github.com/dayour compose into one coherent control plane for the Microsoft Scout fleet (Frontier v0.22.333) - born from the configuration and deployment of Scout to the Cypherdyne (timelarp) tenant.

Overview

Microsoft Scout is Microsoft's first "Autopilot" agent - a Frontier-tier desktop app that reads/writes files, runs shell, drives a Playwright browser, and queries M365 via Work IQ. Once Scout was unblocked on the Cypherdyne tenant, we built a full software-engineering platform around it: an object model, a 16-route control-plane API on the DarbotLM gateway (10.1.8.69), and six repositories that turn the running fleet into programmable, composable, observable infrastructure - what we call Architecture Intelligence.

The control plane

scout-api exposes the fleet as /scout/* routes (health, info, catalog, fleet, nodes, policy, policy/render, sessions, tasks, manifest, schema), backed by scloud-om (Pydantic object model: Node/Agent/Policy/Session/Task/Fleet/Resource/Catalog).

The stack shape

scout-swe (framework) runs on aether (runtime) and is composed by weave (orchestration). scout-sdk is the canonical client; scout-app exposes it over MCP; scout-cli drives it from a terminal.

Identity & auth - ClippyClaw Entra app registration

The control plane is only half the picture. Before any node can sign in to Cypherdyne and clear the Frontier gate, the desktop client (Scout / ClippyClaw) authenticates through a single Entra app registration. This is the identity layer of the architecture - incorporated here from the canonical record in swe_clippyclaw_app_reg.html.

Why it is shaped this way

Public client, no secret - a desktop app can't keep a secret; MSAL uses interactive + device-code + silent-refresh flows, zero credentials shipped.

Deep-link redirect, not localhost - registers custom scheme ms-clawpilot://; Electron intercepts via second-instance (Win/Linux) or open-url (macOS). Satisfies SPACE/compliance (no localhost web reply URL).

Delegated only - all Graph scopes act as the signed-in user; never application permissions. Source of truth: electron/auth/msal-provider.ts + deep-link-loopback.ts + electron-builder.json5.

How it fits Architecture Intelligence: this app-reg is the front door. MSAL acquires delegated Graph tokens which power Scout's Work IQ (mail/calendar/files/Teams/people); the same signed-in account holds the M365 Copilot license that satisfies the Frontier policy gate. Provisioning a new node therefore needs both - the policy key and a sign-in through this registration. The registration ships with an idempotent installer (New-ClippyClawAppRegistration.ps1, with .sh / .cmd variants) embedded in the app-reg wiki.

# darbot-browser-capture

Capture clean, content-only screenshots with the `darbot-browser` tools while
bound to a real Edge profile / appdata, and emit a machine-readable step+schema
for every action.

## Communication standard

NO EMOJIS. Never use emoji characters, decorative Unicode symbols, or markdown
emoji shortcodes in any output, file name, alt text, caption, commit, or schema
value. Use plain text labels instead: `WARNING:`, `NOTE:`, `OK:`, `BLOCKED:`.

## When to use (vs copilotbrowser-capture)

- The session must run as a specific signed-in account/profile (appdata bound),
  e.g. `darbot@timelarp.com` on the Cypherdyne tenant.
- You need to preview a local `file://` HTML artifact (copilotbrowser BLOCKS
  `file://`; darbot-browser ALLOWS it).
- Everything else about privacy and step+schema matches copilotbrowser-capture.

## Profile / appdata connect (darbot@timelarp.com, Cypherdyne)

1. Use `browser_list_profiles` to enumerate the Edge profiles available in the
   configured user-data directory.
2. Use `browser_switch_profile` to select the profile that is already signed in
   as `darbot@timelarp.com` (Cypherdyne tenant). This reuses the existing
   appdata session so no interactive sign-in is needed.
3. If saved Darbot session state exists, `browser_switch_profile` (session
   restore) can re-open cookies/localStorage/URL for that account.
4. Verify with `browser_snapshot` that the destination renders as the intended
   account before capturing. Do not capture the account picker or sign-in.

NOTE: Cypherdyne tenant id 6b104499-c49f-45dc-b3a2-df95efd6eeb4;
timelarp.com maps to cypherdyne.ai. Do NOT print the UPN, tenant name, or ids
into any captured image.

## Privacy-conscious capture rules

1. `browser_take_screenshot` captures the page render region only, not the OS
   window frame, address bar, tab strip, or bookmarks. Prefer it over any
   OS-level full-window grab.
2. For a single panel, pass `element` + `ref` from a prior `browser_snapshot`
   so the shot is cropped to that element and excludes chrome.
3. Never capture the address bar. If a URL, tenant, UPN, or token appears in
   page content, crop it out with an element shot or reframe first.
4. Do not capture sign-in / account-picker screens. Capture only the
   post-auth destination content.
5. Keep full-page captures off unless the entire scroll height is required.
6. Descriptive, non-sensitive file names only (`01-overview.png`).

## Standard capture loop

1. `browser_list_profiles` then `browser_switch_profile` to bind the account.
2. `browser_navigate` to the destination URL (or a `file://` local artifact).
3. `browser_snapshot` to get refs.
4. `browser_take_screenshot` with `element` + `ref` (preferred) or viewport.
5. Copy from the Temp output dir into the shots directory.

## Step + schema convention

Each step is one JSON object; the collection is the automation spec and the
screenshots are the runbook.

```json
{

  "tool": "browser_switch_profile",

```
